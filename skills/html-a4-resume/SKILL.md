# Bilingual A4 Resume

제공된 경력·프로젝트 자료로 간결한 한·영 이력서를 만든다. 기본 산출물은 **한국어 HTML·PDF와 영어 HTML·PDF 총 4개**다. 사용자가 한 언어나 형식만 요청하면 그 요청을 따른다. 특정 개인, 회사, 경력 DB의 구조를 전제하지 않는다.

## 자료와 주장

기존 이력서, 경력 기록, 프로젝트 README·코드·로그, JD, 제출 조건부터 읽는다. JD가 없으면 목표 직무를 기준으로 작성하며, 채용 공고를 필수 입력으로 요구하지 않는다. 지원 직무·언어·분량·마감·회사 양식이 자료에 있으면 다시 묻지 않는다. 중요한 사실 누락은 묶어서 질문하고, 답과 무관한 근거 정리와 레이아웃은 진행한다.

작업용 근거표에 `주장 / 기간·역할 / 개인 기여 / 결과·조건 / 출처 / 확인됨·본인 진술·목표·미확인`을 기록한다. 팀 성과와 개인 기여, 기존 오픈소스와 직접 구현, 실제 장비와 시뮬레이션을 구분한다. 코드 존재를 실행 성공으로 간주하지 않는다. 숫자·고객·직함·기간·숙련도를 만들지 않는다. 검증하지 못한 필수 사실은 보수적으로 표현하거나 초안의 누락 목록에 남기며, 근거표와 내부 QA 메모를 제출용 본문에 넣지 않는다.

공개 키트에는 개인 경력 DB·연락처·실적·로컬 경로를 포함하지 않는다. 학생의 실제 이력서는 허가된 개인 출력 폴더에 저장한다. 이 스킬 자체는 저장소 공개, 지원서 제출, 이메일 발송을 승인하지 않는다.

## 작성 전: JD 기준과 인수조건

JD가 있으면 본문 작성 전에 [공유 JD 기준](../jd-application-review/references/jd-criteria.md)을 읽고 필수요건·주요업무·우대사항, 배점, 문서별 인수조건과 사용할 근거를 정리한다. 한국어·영어 이력서를 모두 평가 대상에 포함한다. 같은 지원 건의 기준이 이미 있으면 그대로 사용하고 포트폴리오와 공유한다. 무엇을 어떤 근거로 보여줘야 하는지와 부족한 실제 경험을 먼저 알린 뒤, 기준에 맞춰 요약·역량·경력 순서를 정한다. JD가 없으면 목표 직무 기반 임시 계획으로 작성하되 JD 적합 점수를 만들지 않는다.

리뷰 스킬에서 기준 ID와 수정사항을 전달받았다면 기준을 다시 만들지 않고 해당 수정만 수행한다. 수정 전에 v1을 보존하고 모든 언어의 HTML·PDF를 갱신한다.

## 구성과 문체

작성 전에 [writing-and-evidence.md](references/writing-and-evidence.md)를 읽는다.

- 이름 → 지원 직무 → 연락처·근거 링크 → 짧은 요약 → 핵심 역량 → 경력 또는 프로젝트 → 학력·자격·수상 → 기술·언어를 기본으로 한다. 학생은 프로젝트·학력을, 경력자는 관련 경력을 앞세운다. 비어 있는 섹션은 삭제한다.
- 학생·신입은 A4 1쪽, 경력자는 1~2쪽을 시작점으로 삼되 제출 조건과 실제 자료량을 우선한다. 언어별 페이지 수는 달라도 된다. 16:9 슬라이드나 긴 자소서 문단으로 바꾸지 않는다.
- 한국어 경력·프로젝트 불릿은 **설계·구현·분석·검증·개선·담당 등의 명사형 종결**을 기본으로 한다. 범위와 행동·결과가 남는 문장을 쓰고, 사용자가 다른 문체를 지정하면 따른다.
- 영어는 **구체적인 동사로 시작하는 자연스러운 비즈니스 불릿**으로 작성한다. 완료된 일은 과거형, 현재 업무는 현재형으로 구분한다. 한국어 어순이나 명사형을 그대로 번역하지 않는다.
- 한 불릿에 한 가지 핵심 행동·결과를 담고 대부분 1~2줄로 편집한다. 성과 수치가 없으면 구현물·검증 조건·운영 범위를 구체적으로 쓴다. 도구 목록만으로 역량을 주장하지 않는다.
- 한·영 버전에 기간·직함·기여 범위·단위·분모·측정 조건·실측/목표 상태를 동일하게 반영한다. 내부 제품명은 처음에 일반적인 제품 종류와 함께 설명한다.

## HTML과 PDF 동시 제작

[layout-and-export.md](references/layout-and-export.md)를 읽고 [resume-ko.html](assets/resume-ko.html)과 [resume-en.html](assets/resume-en.html)을 개인 출력 폴더로 복사한다. 템플릿은 작성 안내 예시이며 실제 지원자 실적이 아니다. 두 파일의 안내와 빈칸을 실제 자료로 교체한다.

기본 파일명은 `resume-ko.html`, `resume-ko.pdf`, `resume-en.html`, `resume-en.pdf`다. 이름·회사·버전 규칙이 있으면 네 파일에 일관되게 적용한다. 기존 지원서를 덮어쓰지 않는다.

- A4 세로 210×297mm, 흰 바탕·검정/회색, 본문 한 흐름, 이름·섹션 제목·기간의 일관된 위계로 구성한다.
- Pretendard를 우선하되 없으면 한글 지원 시스템 폰트를 사용하고 대체 사실과 출력 결과를 확인한다. 개인 컴퓨터의 절대 폰트 경로와 필수 외부 폰트 다운로드를 넣지 않는다.
- 본문 10pt, 좌우 약 16mm 여백을 시작점으로 삼는다. 글자 축소나 잘라내기로 분량을 맞추지 않고 중복 문구를 줄이거나 페이지를 추가한다.
- 읽을 수 있는 HTML 텍스트와 실제 `a href` 링크를 사용한다. 이미지로 본문을 만들지 않는다. 각 언어의 HTML을 Chromium으로 각각 출력해 같은 내용의 PDF를 만든다.

## 검증과 전달

1. 두 HTML을 각각 PDF로 출력한다. HTML만 만든 상태를 PDF 완료라고 말하지 않는다.
2. PDF를 다시 열어 페이지 수·A4 세로 규격·텍스트 추출·한글·영문·실제 링크 주석을 확인한다. `tools/check_pdf.py --kind resume`를 사용하거나 동등한 도구로 검사한다. 2쪽 초과가 요청되면 `--max-pages`로 해당 한도를 설정한다.
3. **두 PDF의 모든 페이지를 이미지로 렌더링해 확인**한다. 잘림, 겹침, 작은 글씨, 제목 고립, 잘못된 줄바꿈, 빈 추가 페이지, 푸터 충돌을 수정하고 다시 출력한다. 자동 검사는 시각 검수를 대신하지 않는다.
4. 한·영 사실 대조와 함께 본문·파일명·제목 메타데이터·푸터에서 이전 지원 회사·직무, 안내 문구와 빈칸을 점검한다. 링크 대상의 접근 가능 여부는 확인한 범위만 보고한다.
5. **4개 파일을 모두 전달**하고 실제 생성·자동 검사·시각 검수 범위와 남은 사실 확인 항목을 간단히 알린다. 출력 도구가 없으면 HTML과 실행 가능한 출력 방법을 제공하되 PDF 미생성을 명시한다. 사용자 승인 없이 전역 도구를 설치하지 않는다.

JD가 있는 새 작성의 1차 출력 후에는 [JD 리뷰·수정 스킬](../jd-application-review/SKILL.md)로 같은 기준의 점수·사실·공개 범위를 검수하고 2차 업데이트한다. 사용자가 작성만/리뷰만 등 범위를 지정하면 따른다. **리뷰 스킬의 수정 단계에서 호출된 경우에는 여기서 리뷰를 다시 호출하지 않고**, 갱신한 파일과 검사 결과를 호출자에게 반환한다.
